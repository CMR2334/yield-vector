## Context
Yield Vector is now 17 ES modules + a thin entry bootstrap + sw.js (v2026.07.09b live; run 2026-07-08-module-split-efficiency complete). The existing `runOptimizer` (js/projection-optimizer.js) is a FEASIBILITY checker: a candidate set passes iff `shortfallDays === 0 && belowBufferDays === 0` over `generateProjection`'s day-by-day capital model. This run builds the SEQUENCER on top: choose which candidate offers to pursue and slide each `plannedSignupDate` within its allowed window to maximize return, subject to the buffer floor and every timing constraint the projection already models (funding deadlines, DD windows + business-day shifts, hold anchors incl. open-date vs funded-date, withdrawal eligibility). In-browser, zero build step, deterministic, phone-first. PRIME DIRECTIVE inherited: zero regression to existing features; the feed, parser, and sync surfaces must stay byte-stable except where the design doc declares UI additions.

## Key decisions (DRAFT — codex critique + owner approval pending)
- Engine = NEW pure module `js/optimizer-engine.js` (state in → plan out; no DOM, no App/Sync imports; consumes projection-optimizer + offer-model + date-format-core exports). Deterministic and seedable; explicit tie-break rules so identical inputs always produce identical plans.
- Search = discrete date-grid per offer (allowed window from offer constraints; coarse weekly steps + deadline-snapped candidate dates) explored with bounded greedy-with-lookahead/beam search — NO external solver, NO approximation of the capital curve: every evaluated sequence is scored by the REAL `generateProjection` (buffer floor enforced exactly as the feasibility checker does). Perf budget: interactive (<~2s) for ~10–20 candidates on a phone; iteration budget + early-out documented and asserted in pins.
- Objective: maximize total expected bonus; tiebreak by annualized return on locked capital, then earlier completion. Buffer floor is a HARD constraint (a plan violating it is invalid, never "penalized").
- Churn-hybrid (owner-agreed design): churn-eligible offers enter the candidate pool valued at their stored bonus, BADGED "stored value from <date> — unverified"; a prompt-gated re-check via the existing DoC URL-import Worker path can refresh the value before/after optimization. The engine treats values as given; ONLY the UI carries the verified/unverified distinction.
- Plan output is TRANSIENT (like a DoC parse result): nothing persists until the owner explicitly applies; apply writes `plannedSignupDate` (and include/exclude selections) through existing update paths as one undoable action class.
- UI lands in the Plan tab per the owner's layout-mock decision (Variant A/B/C — pending at plan time). Engine steps do NOT block on the layout choice; the UI step is sequenced after it.
- Gates: the full existing battery stays green at every step boundary (fidelity 67/67, pins 20/20, p2b, feed byte-identity, preview E2E + 380px) PLUS new optimizer pins: fixture states with hand-verified expected plans, property assertions (never violates buffer; never schedules before today; respects every per-offer window; deterministic across runs), and a perf-budget assertion.

## Plan-gate amendments (BINDING — codex critique 2026-07-08 21:0x; supersede conflicting draft lines above)
- [P1-1] Feasibility input semantics: the engine NEVER passes a bare includedOverride — offerIsActiveForProjection returns ONLY the override set when one exists (offer-model.js:522), which would drop confirmed/open offers. Evaluated set = all currently-active offers ∪ plan candidates at candidate dates, constructed explicitly.
- [P1-2] True purity: every App.state read in the evaluation call graph is INJECTED — ddTransferConfig (dd-widgets.js:4) reads App.state.settings.ddTransfer directly; step 3 includes a sweep for any others. Engine input = a fully self-contained snapshot (incl. settings.ddTransfer); the node harness must exercise altered-settings variants.
- [P1-3] Co-scheduling: decision variables include plannedSignupDate + optionalPlannedFundingDate + directDeposits[].plannedDate as a coherent group (default preserves current relative offsets with business-day-aware re-anchoring; the design doc defines group-shift rules per offer type incl. Held+DD lump-sum + per-DD holds and DD round-trip cash-out windows). Sliding signup alone is INVALID — the cash curve keys off funding/DD dates.
- [P1-4] Qualification validator: cash-feasibility alone never validates a plan. Explicit per-offer checks — expiry, deposit deadline, debit deadline (debitDeadlineISO), user-requirement deadlines, DD window-end + weekday minima — via existing helpers. Plan valid iff cash-feasible AND fully qualified.
- [P1-5] Horizon: engine computes the horizon from the PLAN (max withdrawal-eligible/qualification date + margin) and passes it explicitly — no reliance on effectiveHorizonDays' active-offers-only 180-day clamp. Horizon-overrun fixture required.
- [P2-1] Churn synthesis: candidates built via the Run-again pipeline semantics (templateToOffer(offerToTemplate(o))); snoozed churns EXCLUDED; missing anchor dates → not a candidate (surfaced as "needs date"); value-date precedence: last_edited → template savedAt → "unknown", with distinct badge copy per source.
- [P2-2] A Worker re-check that changes ANY optimization input (bonus, funding, expiry, hold anchor, tiers) triggers a full RE-RUN, not an annotation update.
- [P2-3] Tiered offers: NEVER auto-pick a tier; an un-chosen tier ladder optimizes at the stored offer bonus, badged; optional pre-optimization tier prompt in candidate review.
- [P2-4] Candidate dates: business-day-aware local neighborhoods (±1–3 business days) around anchors — today, funding deadlines, expiries, capital inflow/outflow events, withdrawal releases, DD weekday minima; coarse weekly pass only across wide-open windows, then local refinement. One-day weekend/holiday shifts materially change DD round-trip dollar-days.
- [P2-5] Determinism + escape from local optima: tie-break on the full sorted (offerId, date) vector, never incidental array order; pair-swap/local-repair pass after the beam; exact enumeration for small candidate counts (≤~7).
- [P2-6] Apply flow: a dedicated applyOptimizerPlan action mirroring modal-save semantics (last_edited stamping, syncRequirementsWithLegacy, DD id preservation) with a one-shot undo snapshot of every mutated field; NO bare App.update scatter-writes; feed/action-tombstone implications specified in the design doc.
